Runs pytest with MSYS2's UCRT64 python3.exe under Wine, on an export of HEAD in STATE/scratch/wine/tree (`rm -rf tree; mkdir tree; git archive HEAD | tar -x -C tree`, then copy changed files in). It needs the MSYS2 tree STATE/probes/wine_windows_build.sh unpacks (scratch/wine/msys/root) and pure-Python pytest, _pytest, pluggy, iniconfig, pygments copied from the host's site-packages into scratch/wine/pylib (PYTHONPATH). Run it as `env -u WAYLAND_DISPLAY timeout -k 5 60 xvfb-run -a STATE/probes/wine_pytest.sh test/<file>.py -q -p no:warnings > out.txt` and grep the file.

- It reproduces the Windows CI for what the CI runs without MSYSTEM: the cp1252 decoding errors, WinError 32 on open files, drive-letter paths, the CSD title bar, the Windows branches of portability.py. Checked on eleven CI failures that failed under Wine before a fix and passed after.
- **wineserver -k before each run** (the script does it): a wineserver left from an earlier xvfb display makes Gtk.init fail in the next run ("Gtk couldn't be initialized").
- **GDK_BACKEND unset, not empty**: an empty GDK_BACKEND also stops GTK initialising.
- **No PYTHONUTF8**: Windows runs in the ANSI code page (cp1252 on the runner, and in the de_DE Wine prefix), which is what finds the encoding bugs.
- **Set PYTHONUNBUFFERED=1 first when runs stall** (at 52549440): runs stalling at the limit with no pytest output, on two small files: 7 of 8 without it, 0 of 4 with it, in one session. Python and Gtk.init_check() alone ran fine meanwhile. Too few to say why, and an earlier session saw stalls with it set ("Windows: what the tests must not assume"). In zsh `$flags` does not split: exit 4 is pytest refusing "-q -s" as one argument.
- **Not faithful everywhere**: some chooser tests fail in teardown with WinError 145 (rmtree timing), the prefix has no 7z and no SVG loader, test_windows_build and test_pdf_multi (worker processes) hang, and a whole large file overruns 60 s. Trust Wine for a failure that matches the CI log; an extra Wine-only failure is not evidence. Without 7z, test_archives.py under Wine fails 26 tests that unpack a nested .7z or a tar.xz through 7z (RecursiveArchiveFormat*RedAndBlues, 7zExternalTarXz); the runner passes them. (corrected at 7a139017)
- **Copy UnRAR64.dll in before a change to a RAR handler** (at 7a139017): without it every RarDll test skips, so Wine says nothing about them, and 9bb28a35 passed here and then failed 16 tests on the CI. win32/fetch_unrar.ps1's DLL is at scratch/unrar-fetch/out; copied to scratch/wine/msys/root/ucrt64/bin (WINEPATH) it loads, and `-k "RarDll and Glob"` then reproduced the CI's 16 exactly. Rebuild the MSYS2 tree and it has to go in again.
- **A fix can fail the suite by being right** (at 7a139017): test_archives' expected failures are strict, so a handler change that cures one shows as "Unexpected success". Before calling a change to a handler done, read `xfail_list` for what it might cure, the block for `win32` too, which this machine never runs.
- **The prefix's user folders were links into the real home** (Desktop, Documents, Downloads, Music, Pictures, Videos -> /home/<user>/...). They were replaced with empty directories at 17788a60; a new prefix has them again, and must be treated the same before anything runs in it.
- **Windows file attributes hold under Wine** (at f8bf831d): `ctypes.windll.kernel32.SetFileAttributesW(path, 0x2 | 0x4)` on a folder in a test, then `os.stat(path, follow_symlinks=False).st_file_attributes`, reads HIDDEN and SYSTEM back, so a test of code that skips hidden or system folders proves the attribute branch under Wine, not only the leading-dot one. A name like `$RECYCLE.BIN` keeps the dot rule from passing it by accident. To run a few changed files under Wine, copy them over their copies in STATE/scratch/wine/tree rather than exporting the whole tree again.
- **Deleting an open page is flaky under Wine (ad0dea08)**: test_file_handler.py DirectoryWalkTest test_a_loose_page_is_available_for_as_long_as_its_file_is_there and test_refreshing_a_deleted_picture_opens_the_next_one failed once at HEAD, and 2, 0 and 1 times of 2 in three runs with a change that does not touch deletion; Wine's sharing of an open file is not Windows'. Not evidence either way. Run test_file_handler.py by class under Wine: the whole file overruns 270 s.
- **Run the whole class of a Windows-only branch's tests under Wine, not just the new ones (at 6b4dba97)**: ad0dea08's win32 branch in book_area called release_archive() on test_book_area's stand-in _OpenBook, which lacked it; the two new tests passed under Wine, two older DeleteFromDiskTest tests failed on the runner (Windows tests 42358779603). `-k DeleteFromDiskTest` under Wine reproduced both.
- **test_library_types.py fails 4 under Wine at a80d956f and before it** (CollectionTest x3, WatchListEntryTest.test_valid_dir: a 7z archive counted 1 != 2), while the Windows runner passes them: the Wine MSYS2 tree, not the code. Compare with the file at HEAD before blaming a change.
- **Name tests by node id in test_main_window.py** (at dd965597): `-k shuffle` over the file overran 120 s with no pytest output (collection of the whole file under Wine), while `test/test_main_window.py::MainWindowTest::<test>` for two tests passed in 2.4 s and for four in 2.4 s. The file has one huge class, so "run by class" does not help there.
- (added at 25e6fd59) **Wine draws on the real display unless given another**: `probes/wine_pytest.sh` ran `wine` with the session's DISPLAY until 2026-11-15, and test_shelf.py's main windows came up on the user's screen. The probe now wraps wine in `xvfb-run -d` and unsets WAYLAND_DISPLAY; wine_gdb_pytest.sh and wine_start_trace.sh re-run themselves under `xvfb-run -d` (WINE_PROBE_ON_XVFB marks the inner run), and wine_windows_build.sh already used xvfb-run (test_shelf.py: 10 passed that way). Any other command that starts wine (the build, a probe of its own) needs the same wrapping.

A RAR made on Windows, without Windows: `rar a` on Linux writes host Unix and the mode bits, and the UnRAR DLL under Wine maps a Unix 0444 to a writable file. `STATE/probes/rar_windows_host.py <in.rar> <out.rar>` rewrites each RAR 5 file header to host Windows and attributes 0x21 (read-only, archive), keeping the vint's length with redundant continuation bytes and recomputing the header CRC; `unrar vt` then shows `..A...R` and `Host OS: Windows`, and `unrar t` passes. UnRAR64.dll 7.23 under Wine extracts such members read-only, and Wine refuses to delete them as Windows does (481850ea, test/files/archives/ReadOnlyFromWindows.rar).
