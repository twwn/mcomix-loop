- **A zip name without the UTF-8 flag is whatever its writer used**; zipfile reads it as cp437, and `name.encode('cp437')` gives the bytes back. Decode all such names of an archive together: UTF-8 if all are, else chardet over the joined bytes (a single name is too short - it read Shift-JIS "表紙.jpg" as Windows-1252, the four together as Shift-JIS at 0.99). A test builds such a zip by writing ASCII placeholders of the right byte length and replacing their bytes in the file; make the placeholders one repeated letter each, since zero-padded numbers are found inside one another.
- **ComicInfo.xml**: expat hands an unknown declared encoding to Python's codecs, which raise LookupError, not ParseError (67ebd5ad). UTF-16 with or without a declaration, and UTF-8 with a BOM, parse.
- (at a810b155) **Tar names and lone surrogates**: tarfile decodes names as UTF-8 with surrogateescape, and GTK refuses a surrogate in any label or title (Gtk.Label.set_text raises UnicodeEncodeError), as does the log handler ("--- Logging error ---"). archive_base.name_encoding() picks one encoding for all of an archive's undecodable names (UTF-8, chardet, then a fallback that decodes any byte: cp437 for zip, Latin-1 for tar). A test writes such a tar with tarfile.open(..., format=GNU_FORMAT, encoding='latin-1'); give each encoding names it can encode. External archivers' listings go through i18n.to_unicode, which never leaves surrogates. Left: file names on disk that are not UTF-8 (os.listdir surrogates) in a folder book.
- (at ffd831e9) **Paths on disk that are not UTF-8** (Python's lone surrogates, e.g. os.fsdecode(b'B\xfccher.cbz')) break everything that must be UTF-8: GTK labels and titles, GVariant strings (a menu action's target: carry paths as 'ay' with os.fsencode), SQLite text (the library: backend.storable() keeps such books out), and strict standard output (the log formatter escapes them). The title bar already used i18n.to_display_string. Build such a file in a test with os.path.join(os.fsencode(tmp), 'B\xfccher.cbz'.encode('latin-1')). JSON preferences are safe: json.dumps escapes surrogates by default. Not yet looked at: the watch list's directories (SQLite again).
- (at 1b6cb92f) **7z passes a zip name without the UTF-8 flag through as its stored bytes** even with -sccUTF-8, so its listing must be decoded with surrogateescape and the names read back with archive_base.surrogate_name_decoder(), as tar's are. A zip reaches 7z (ZIP_EXTERNAL) when its compression is not stored or deflate: zipfile.ZipFile(..., compression=zipfile.ZIP_BZIP2) makes one for a test. The unzip handler, second in line, lists such names in mojibake but does not fail; left alone. The watch list stores directories as SQLite text too (de0e3d24): backend_types.storable() now guards the library, the watch list and a scan's new files.
- (at 63f08924) **PyMuPDF takes a file name only as UTF-8 text** (not bytes, not a file object; only a name or the whole document as a stream), so a PDF at a path that is not UTF-8 is opened through /dev/fd/N of a descriptor opened on it (child._open). A probe that makes such a PDF saves it under an ASCII name and renames it, since document.save() refuses the path too. 7z prints the archive's own path at the head of every listing: decode its output with surrogateescape.
- **7-Zip for Windows decodes flagless zip names itself** (at ade25ade): the runner's build in the OEM code page ("├£bersicht" for UTF-8 "Übersicht"). `-mcp=<code page>` applies when reading: 28591 (ISO 8859-1) gives each byte back as the same-numbered character. The 7z format refuses `-mcp` ("opening : invalid parameter"); Linux 7z ignores it and prints raw bytes. `-slt` marks flagged zip entries `Characteristics = UTF8` and the header says `Type = zip`.
- **Windows 7-Zip under Wine**: MSYS2's mingw-w64-ucrt-x86_64-7zip (26.03, from repo.msys2.org/mingw/ucrt64/) unpacked into scratch/wine/7zip; scratch/wine/pt7z.sh is STATE/probes/wine_pytest.sh with that bin dir first on WINEPATH, so sevenzip_external finds 7z.exe. Run by hand from a shell it printed flagless UTF-8 names correctly, but run by MComix under pt7z.sh it reproduced the runner's cp437 mojibake exactly - trust the pytest run, not a hand run.
- **chardet 7**: `detect(..., encoding_era=EncodingEra.MODERN_WEB)` (chardet 6's default) reads modern code pages right, but confidences are on another scale (0.01-0.43 when right, DOS code pages wrong at up to 0.027): i18n.guess_encoding() applies the 0.5 cut to chardet < 7 only. Measurements: SCRATCH chardet_*.py scripts at 5b29e87d, rerun with the floors venv (chardet 7.6) and the system Python (6.0).
- **Archive names in a legacy code page, measured** (at d542032d): `STATE/probes/names_bench.py` runs name_encoding() over sixteen name sets (six written by DOS, ten by Windows, CJK) and prints which read right; run it with the system Python (chardet 6) and the floors venv (chardet 7). chardet cannot tell single-byte code pages apart by their bytes; what tells them apart is whether the non-ASCII characters come out as letters (name_encoding's _letter_share). At d542032d: 15 of 16 right under chardet 7, 12 under chardet 6.
- **Comments in a legacy code page, measured** (at 764dd88f): `STATE/probes/comment_bench.py` runs i18n.to_unicode() over eleven texts; 10 of 11 right under either chardet (Russian in cp866 is the one left: cp866 reads every high byte as a Cyrillic letter, so it cannot be a candidate of the letter-share choice without taking over other texts). i18n.best_decoding() is the one choice both names and comments use.
- **Watching an encoding fix fail on a UTF-8 machine.** A bare `open()` uses the locale's encoding, which cannot be patched in-process (the C code reads it directly).  Run the test file under `env LC_ALL=C PYTHONUTF8=0 PYTHONCOERCECLOCALE=0` - all three, or Python coerces the C locale to UTF-8 - and `locale.getencoding()` is `ANSI_X3.4-1968`: a missing `encoding="utf-8"` then fails on any non-ASCII text, as it would under a Windows code page.  Keep such a test file free of GTK imports so it runs on its own.
