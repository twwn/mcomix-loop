From the first Windows CI run (7d665a52, 123 failed, 14 errors) and the fixes after it:
- os.path.expanduser() reads USERPROFILE, not HOME; MComix' settings are under APPDATA. MComixTest redirects both, and LOCALAPPDATA; without that, tests wrote C:\Users\<runner>\MComix.
- os.path.isabs('/home/user') is False on Windows since Python 3.13 (no drive); os.path.abspath() adds the current drive, so a path stored raw in the library is not found by get_book_by_path().
- open() without encoding reads cp1252; the repository's files are UTF-8.
- Windows deletes, moves or replaces no open file, and no read-only one (shutil.rmtree needs an onexc that chmods).
- No mode bits on directories, no mkfifo, no getuid, no surrogate-escaped names; posix_byte_names in test/__init__.py skips the not-UTF-8 name tests.
- GIO on Windows has no MIME types for .cbz/.cb7 ("application/x-ext-cbz"); a Gtk.FileFilter pattern is case-sensitive, add_suffix() is not.
- GTK draws the title bar inside a decorated window on Windows (39 px).
- 7-Zip for Windows decodes zip names stored without the UTF-8 flag in the OEM code page before printing them.
- run.wait_and_exit() calls input() on Windows; tests that reach it patch builtins.input.
- (added at c45a9efe) **A closed file chooser holds its folder on Windows until collected**: GTK's directory monitor keeps a handle, so the folder cannot be removed (WinError 145 on its parent) until gc.collect() frees the chooser and the main loop turns. MComixTest's cleanup retries that way; a probe that removes a folder a chooser showed has to do the same.
- (added at 6350e74a) **Wine sometimes stalls before Python prints anything**: about one run in four of STATE/probes/wine_pytest.sh on a small file (test_pageselect.py, 10 tests, 8-12 s when it runs) hit the 60 s limit with no output at all, even with PYTHONUNBUFFERED=1 and pytest's faulthandler_timeout; the stall is before pytest starts, so it is Wine's, not MComix'. Rerun; a timeout with output is a finding, one without is not.
- (added at 6350e74a) **wait_for() warns WaitGaveUp** with the calling line when it runs out of time; in the suite's warnings summary that names every wait that spent its whole timeout. On Linux three do, on purpose: test_page_image.py:126 and :136, test_properties_dialog.py:239.
- (added at ed2b4f94) **On real Windows every pump() ran its full 4000 turns** (likeliest reading of the fourth CI run: the thirty slowest tests, all window tests, 11-14 s in the call phase against well under 1 s on Linux and about 1 s under Wine). pump() now also stops after a second and warns PumpNeverIdle with the calling line when it stopped with events pending; Linux and Wine show none. The flood of gtk_im_context_ime_message_filter criticals in the Windows log is the suspected always-pending source. The warnings summary of the next Windows run confirms or refutes it. (corrected at 85e30237) Refuted: the next run (logs_98277634996) warned PumpNeverIdle once and had no criticals, and its slowest thirty tests still took 12.6-13.8 s each. adac48fc adds a workflow step that runs three of them alone under cProfile.
- (added at 37cde42f) **Alone, Windows window tests are fast**: adac48fc's profile step ran three of them in one process at 0.37-0.70 s (logs_98281449321), against 11-14 s for their kind in the full -n auto run. 7adc063b warns RemovalWaited when teardown had to retry removing a folder; 6d694967 profiles the full run's slowest tests alone; 37cde42f runs the crash files under MSYS2's gdb for a C stack.
- (added at 37cde42f) **Under Wine a chooser test's "home" stays delete-pending for good**: 8 of 13 test_file_chooser tests spend 5 s in _make_writable_and_retry and fail (WinError 145 on the test directory, "home" empty but listed). The ones that move the chooser elsewhere (set_file into another folder) do not. Neither run_dispose() on the Gtk.FileChooserWidget nor emitting its "recent-shortcut" signal on unrealize freed it under Wine, so the holder is not settled; real Windows lets go (the tests pass there). STATE/probes/timeline.py (a -p plugin, copy into scratch/wine/pylib) prints each test's time in run order.
- (added at 985506cf) **The Windows access violations were GTK's IME message filter left behind by a destroyed window** (gtkimcontextime.c, GTK 4.24.0 and main; GTK issue 8289): focus_in() adds gtk_im_context_ime_message_filter to the display, only focus_out() with a live surface removes it, dispose() does not. A window destroyed with a text field focused leaves a filter pointing at a freed context; every later window message runs it (criticals, then a crash in DestroyWindow or present()). widgets.drop_focus_when_closed() clears the focus from an 'unrealize' handler (runs before GTK's own, surface still there); Dialog, MainWindow and the library window use it. **A new Gtk.Window subclass must call it too.** Test pattern: focus a Gtk.Entry, destroy, record window.get_focus() from the entry's 'unrealize': must be [None].
- (added at 985506cf) **gdb on Windows, stripped DLLs: STATE/probes/symbolize_gdb.py** names the frames of a backtrace: it finds the one 64 KiB-aligned load address at which every return address follows a call in the DLL's llvm-objdump disassembly (8 of 8, unique, for libgtk-4-1.dll), then takes the nearest exported symbol. Needs the same MSYS2 package build locally (STATE/probes/msys2_resolve.py fetches them; the versions are in the setup-msys2 step's log). The step: `gdb -batch -ex run -ex "bt 40" --args python -m pytest -q -p no:xdist -p no:faulthandler <files>`; pytest's dots do not show which test was running. (added at 2dad5916) Such a step reruns its own files in its own process: it never sees the xdist workers' crashes in the pytest step, and it yields one stack at most (the fault ends the process). With no fault gdb prints "No stack." and exits 1. It was dropped once the crashes stopped (2dad5916); 37cde42f has it.
- (added at 985506cf) **Windows slowness is not in the tests themselves and not in folder removal**: in logs_98285004625 the full run's slowest (11-13 s) took 0.6-1.4 s alone (59 tests in 32 s, one process), and the full run warned RemovalWaited not once. What remains is something that grows within a long worker; the leaked IME filters above (one more per destroyed window with a focused field, each run for every message) fit. Alone, GLib's MainContext.iteration() costs 4.4 ms per call on the runner (2155 calls, 9.6 s of 32 s).
- (added at 6db038e9) **The Windows slowness is growth within a process, and Linux has it too.** test_main_window.py in one process: 0.45/0.63/0.81/1.03 s per test by quarter on the runner (logs_98334836687), 0.073/0.099/0.132/0.152 s on Linux. Every test's MainWindow stays alive: STATE/probes/growth.py (a -p plugin) printed +2,170 Python objects and +120 GObject wrappers per test, no toplevels or threads left; STATE/probes/window_holders.py lists what refers to the oldest window at session end (its own parts, and bound methods held by GTK). Ruled out on Linux: Python GC scanning (gc.freeze() after each test changed nothing), accessibility (GTK_A11Y=none), display CSS providers (removing MainWindow's and the thumbnail bar's on unrealize changed nothing), window hide/destroy (0.1 ms, flat). STATE/probes/growth_profile.py profiles the first and last quarter apart: it found RecentFilesMenu rebuilds 550 -> 5,496 (fixed 6db038e9: 73 -> 87). Its tottime for terminate_program (+2.3 s) was an artefact: timing the steps directly showed 2.9 -> 5 ms. Releasing a destroyed MainWindow like a dialog (widgets.release plus cutting its action groups' handlers) failed all 64 tests and freed none: a campaign.

The Windows runner's Pillow is newer than Linux's, so its warnings summary shows such deprecations first.
