- (at 6c8f3118) **How long MComix.exe ran before Python started**: `portability.seconds_since_process_start()` reads the creation FILETIME with `GetProcessTimes` and the clock with `GetSystemTimeAsFileTime`, both as `ctypes.c_uint64` (FILETIME is two little-endian DWORDs), 100 ns units. `run()` logs it as the first debug line ("Python started N s after the process"), then "Loading GTK", "Building the main window", "Started" (an idle callback once the main loop runs). A slow start's `-W debug -o` log says which step held it.
- **The pseudo-handle of the current process is passed as `ctypes.c_void_p(-1)`**, not `GetCurrentProcess()`'s return: ctypes' default restype is a C int, and handed back as an argument it goes out as 32 bits.
- **Checked for real under Wine**: export the tree to scratch/wine/tree and run MSYS2's python3.exe there with WINEPREFIX, WINEDEBUG=-all and WINEPATH set as STATE/probes/wine_pytest.sh does: `python3.exe -c "import time; time.sleep(1.5); from mcomix import portability; print(portability.seconds_since_process_start())"` printed 2.09.
- **mypy (warn_unreachable) and platform code**: `if sys.platform != "win32": return None` followed by Windows code is "Statement is unreachable" on Linux; write `if sys.platform == "win32": ...` with the fallback after it, the shape mypy skips.
- **Unit-testing it on Linux**: patch `sys.platform` and `ctypes.windll` (create=True); the Mock's side effect writes the FILETIME through the byref argument's `._obj.value` (test_portability `ProcessAgeTest`).
- **Ruled out for a slow first start on Windows**: GLib's win32 session-bus autolaunch waits at most about 2 s (GLib 2.90, gdbusprivate.c read_shm), and runs only when "single instance" is on. Low CPU in MComix during the wait means it is blocked, not computing (no fontconfig cache, no decoding); an antivirus scanning the DLLs shows its CPU under its own process ("Antimalware Service Executable").

- (added at 6dd8f0b9) **Waiting or computing**: time.process_time() is the process' kernel plus user time since its creation, all threads, on Windows (GetProcessTimes) and Linux alike, so read at mcomix import (mcomix.started_on_cpu) it includes the CPU the loader spent before Python ran. Under Wine, MSYS2's python3.exe gave 0.01 s at start, 0.1 s for 0.099 s of busy wall time and 0.0 s across time.sleep(1). The start log's phase lines carry it ("(%.1f s of CPU so far)"): wall time far above it is waiting (disk, an antivirus scanning in its own process, whose CPU is not ours); close to it is our CPU (a slow or emulated processor). The user's log at 909baeef had every phase ~100x slower than Linux alike (22.4 s before Python, 32.6 s modules, 25.1 s GTK, 10.9 s image formats, 11.6 s archive modules, 20.7 s to Showing), no single culprit.
