- **Always under Xvfb**, and with X rather than Wayland: `env -u WAYLAND_DISPLAY GDK_BACKEND=x11 xvfb-run -a ...`. A bare pytest run against no display hangs rather than failing.
- **`-n WORKERS` (`STATE/config.sh`; 8 on a 24-core machine) is the measured optimum** for the suite: 27 s for 3,620 tests at dc0c098f (nine seconds against thirty-three serial when it was a third of that size). `-n auto` fans out to every core and is slower: worker startup dominates a suite this short. `--dist loadfile` is the fallback if shared state starts biting.
- **Timeouts belong on every run.** 60 s for the suite and any probe, 120 s for mypy; the suite at 27 s has halved that margin since 16 s, so raise `T_PYTEST` in `STATE/config.sh` before it reaches ~45 s. A longer timeout hides a hang instead of surfacing one — which is how the `_BookArea` hang below was found.
- **Two sessions running gates.sh at once share SCRATCH/pytest.txt** (at a463e922): the log then holds two summaries and stray bytes, gates.sh's grep calls it a binary file and reports "no summary line". While another session is active, run the suite on the export by hand with its output in a log of your own name, and read the summary with `grep -a`.
- **A hand-written check for failures must not match "12 xfailed"**: grep for `(^| )[0-9]+ failed`.
- (at 00e6f348) **A suite that is killed at the timeout near 98 % is not always a hang: look at where its temporary files lie.** `test/__init__.py` keeps its temporary root in `<tree>/test/tmp`, so an export under STATE runs its SQLite tests on the disk, where each commit is an fsync: at 5.2 ms an fsync (50 writes timed with `os.fsync`; 0 ms on a tmpfs) UpgradeFromEveryVersionTest's 10 tests took 19.93 s from the export against 0.57 s in a checkout on /tmp, and the whole suite 72.77 s against 30 s, at 256 % CPU with eight workers. Tell the two apart with a longer timeout and `--durations=25`: a hang has no summary, a slow disk has one and lists the database tests first.
- (at 00e6f348) **pytest 9.2 prints `u` for a passed subtest** and counts "N subtests passed" in the summary; a progress line full of `u` is not a line of failures.
- (at 00e6f348) **A probe that needs a full disk mounts one in a user namespace**: `unshare -Urm sh -c 'mount -t tmpfs -o size=64k tmpfs "$0/full" && exec xvfb-run -d -s "-screen 0 1280x1024x24" timeout -k 5 170 python3 "$0/probe.py" "$0/full"' <dir>`. The guard wants the `timeout` inside the `sh -c`, after `xvfb-run` and directly before the Python run, so that xvfb-run cleans up after a hang (corrected 2026-11-18; it stood before `xvfb-run`).
- (at c4cb82aa) **What a killed run or a probe's `os._exit` leaves in /tmp.** The suite cleans up after itself: a whole `gates.sh pytest` left no new /tmp/pymp-*, /tmp/xvfb-run.* or /tmp/mcomix.* (52, 20 and 20 before and after, 2026-11-17). Two things leave them. (1) `xvfb-run` has no trap: when `timeout` outside it kills it (exit 124), its /tmp/xvfb-run.XXXXXX (Xauthority, pid file) stays; with the command exiting on its own the script removes it. Put the timeout inside, `xvfb-run -d -s ... timeout -k 5 <s> python3 ...`, and xvfb-run sees exit 124 and cleans up. (2) test/__init__.py calls `multiprocessing.util.get_temp_dir()` at import (it pins the folder before MComixTest moves TMPDIR), and only atexit removes that folder, so a probe built on it that ends with `os._exit(0)` leaves one empty /tmp/pymp-*: call `shutil.rmtree(multiprocessing.util.get_temp_dir(), ignore_errors=True)` before `os._exit`. Both shown with a bare `python3 -c` under xvfb-run: killed at 3 s left one xvfb-run dir and no pymp; `get_temp_dir(); os._exit(0)` left one pymp and no xvfb-run dir. /tmp/mcomix.* dirs are the extraction folders of the user's own running MComix windows (their times match the processes' start times): not the tests', not to be touched.
- (at 4e67e413) **What os._exit leaves, and the one line that stops it.** test/__init__.py makes `test/tmp/session.*` (TMPDIR for the run, with its own pymp-*) and removes it from atexit; multiprocessing removes its pymp-* (a socket for the PDF reader's forkserver; Python 3.14 puts it in /tmp when TMPDIR's path is too long for a socket, saying "Ignoring user-defined temporary directory") from atexit too. A probe ending with `os._exit(0)` skips both: 411 session dirs piled up in test/tmp and 55 pymp-* in /tmp, all the loop's. Put `import atexit; atexit._run_exitfuncs()` before `os._exit(0)`: done in bench_shelf_covers.py and extract_threads_bench.py (checked: counts unchanged across a run); 34 other probes still end bare (`grep -ln os._exit STATE/probes/*`), fix each when next used. A test that fails keeps its `test/tmp/<test id>.*` on purpose, for post-mortem: a mutant run leaves one per failing test. A normal pytest run, serial or -n 4, leaves nothing. A real MComix quitting (SIGTERM or Ctrl+Q, a PDF or a ZIP open) leaves nothing in its TMPDIR or /tmp: STATE/probes/quit_real_tmp_left.py.
- (at 82c481b8) **`pump(n)` is no measure of time.** test/__init__.py's pump() returns as soon as the main context has nothing pending, so a probe that waits for a count to settle with `while count != len(made): pump(400)` stops while workers are still busy and the main loop is idle; it reported 16-43 rows "still blank for good" that came 25-32 ms later (lead 34). Wait on time and on the condition: `wait_for(lambda: <all done>, seconds=20)`, then `wait_for(lambda: False, seconds=0.3)` for stragglers. To check what workers do while the main loop must not turn (a result held on the idle queue), sleep in a loop on the pool's own state, e.g. until `view._thread._orders_set` is empty (test_a_thumbnail_on_its_way_is_not_asked_for_again).

## Waiting for frames, not sleeping (added at 56014c2e)

What happens at layout or paint (a scroll, a revealed widget, a CSS colour) is a frame away, not an idle away: `test.wait_frames(widget, frames=3, seconds=5)` in test/__init__.py counts ticks of the widget's frame clock (add_tick_callback) inside wait_for. It replaced fixed sleeps and pump loops of 0.3-1.6 s in test_thumbnail_grid, test_theme, test_shelf and test_properties_dialog (422a45a7, cc0171af). A test that needs real time from the code (a GLib timeout such as SEARCH_DELAY_MS or FolderWatch DELAY, the recent list's whole seconds) patches the constant or the time instead (569e2760, e7e65d88, 2d26a12a). A negative wait ("nothing more comes") waits on what would deliver it - a joined thread, an idle already queued, a Gio monitor's CHANGES_DONE_HINT - then one pump (33f15abe, 59706b3e, e7e65d88).
- (added at 344a4630) **"Nothing more will start" is read, not waited out, when every thread that could start it can be seen waiting.** Wrap the waits the threads park in and count them: `pool._condition.wait` replaced on the instance by a function that counts around the real call (it is called, and returns, with the condition's lock held), and the test's own blocking point (`go_on.wait`) counted under the test's lock. Settled is, read under the pool's lock: the parked plus the held equal `len(pool._threads)`, and any thread parked in the pool has its own reason to wait (`not queue or in_hand >= at_once`) true, so one notified but not yet back re-waits. test_worker_thread.py went from a 0.2 s quiet per count (1.98 s) to 0.49 s; three mutants of worker_thread.py each still failed it. The same shape replaced a 0.5 s negative wait in CoverInFlightTest (cb714df8: wrap `area._reading.wait`, wait until a worker reaches it). A polling-only selection (the file chooser's 200 ms preview timer) is asked at once by the test (`dialog._poll_preview()`), with one test left to the timer so a timer that never runs still fails (41311a55). A process launch is counted by `Gio.AppLaunchContext`'s "launched", emitted inside `launch()` (22c2ac2e).
- (added at 6c8dcf0c) **Timing what a window costs to build: STATE/probes/prof_main_window.py and bench_menu_walk.py**, each copied under test/ (`test/_name.py`, which pytest does not collect in the gates) and run with `-q -s`. prof_main_window builds ROUNDS (env, 20) MainWindows as MainWindowTest does, OPEN=1 with the fixture ZIP, and prints the medians of construction and of the first pump(2000), then cProfile's top 35 by cumulative and own time. Read both numbers: a ZIP opened in the constructor drains the main loop inside it (FileHandler._close), so idles the window left run there, and work moves between the two columns without changing their sum. cProfile's own time of a method that calls GTK is GTK's (gi calls are not listed separately): `_rebuild_menus` showed 14 ms own, which was set_menu_model making popovers. It also inflates recursive generators: `_descendants` (a `yield from` per tree level) showed 10 ms a window and timed 1.1 ms bare. bench_menu_walk times the menu walks, a full menu rebuild, the menu bar and the right-click menu separately. At a6a719d4 and 6c8dcf0c: menus built twice (in MainUI.__init__ and again from the accelerators' idle) and the right-click menu built unopened; a window with a book went from 65.2 to 31.7 ms, without one from 50.2 to 22.3 ms, and the suite from about 30.3 s to 24.8 s.
